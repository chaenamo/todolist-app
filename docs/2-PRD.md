## 1. 개요

### 1.1 배경
도메인 정의서의 문제 정의 P-01(개인별 할일 관리 부재), P-02(기간 관리 부족), P-03(월/주/일 캘린더 조회 불가)을 해결하는 웹 앱을 만든다.

### 1.2 목표
| 구분 | 목표 |
|------|------|
| 제품 | FR-01~08을 충족하는 MVP를 **2일 내** 완성한다. |
| 비즈니스 | **동시 접속 1,000명**을 수용한다 (NFR-01~04로 측정). |
| 운영 | 1인 개발·1인 예산 수준으로 구축·운영 가능한 단순한 구조를 유지한다. |

### 1.3 목표 사용자
- 학생 및 20대~50대 직장인으로, 학업·업무 할일을 기간 단위로 계획하고 캘린더로 한눈에 확인하려는 개인 사용자.
- 페르소나별 상세 시나리오는 작성하지 않는다. 과업·흐름 중심 사용자 시나리오는 `docs/3-user-scenario.md`에서 정의한다.

도메인 규칙은 도메인 정의서 6장(BR), 5장(ST), 7.1절(AC)을 그대로 따른다. 모든 화면은 BR-01, BR-02를 전제로 한다(로그인/회원가입 제외).

### 3.2 PRD 결정 사항 (도메인 정의서 보완)
- 목록 기본 정렬: **종료일자 오름차순, 동일 시 생성일시 오름차순** (Q-05 결정).
- 캘린더 상태 표시: 완료 항목은 시각적으로 구분(예: 취소선)만 한다. 캘린더 필터는 미적용 (Q-03 결정, 필터는 Should).
- '오늘' 기준(A-01)은 브라우저 날짜이므로, 상태 필터 요청 시 클라이언트가 오늘 날짜를 서버에 전달한다. 상세 방식은 후속 API 설계 문서에서 정의.
- API 엔드포인트 명세, DB 스키마(DDL), 컴포넌트 설계는 **후속 문서에서 정의**한다.

## 4. 비기능 요구사항 (NFR)

> 수치는 1,000명 동시 접속 목표에서 도출한 **가정(합리적 기본값)** 이다. 이번 범위에서는 부하 테스트를 하지 않으므로 NFR-01~04는 목표치로만 두고 검증하지 않는다.
> 부하 가정: 동시 접속 1,000명, 사용자당 평균 10초에 1회 요청 → 평균 약 100 RPS, 피크 200 RPS.

### 4.1 성능·확장성
| ID | 요구사항 | 측정 방법 |
|----|----------|-----------|
| NFR-01 | 동시 가상 사용자 1,000명(피크 200 RPS) 부하에서 시스템이 정상 동작한다. (가정) | 부하 테스트(이번 범위 미실시) |
| NFR-02 | NFR-01 조건에서 조회 API(목록·캘린더·토큰 갱신 refresh) p95 응답시간 ≤ 300ms, 쓰기 API(등록·수정·삭제·완료) p95 ≤ 500ms. (가정) | 부하 테스트(이번 범위 미실시) |
| NFR-03 | NFR-01 조건에서 로그인 API p95 ≤ 800ms (bcrypt 연산 포함). (가정) | 부하 테스트(이번 범위 미실시) |
| NFR-04 | NFR-01 조건에서 HTTP 5xx 에러율 < 0.1%, 전체 실패율(타임아웃 포함) < 1%. (가정) | 부하 테스트(이번 범위 미실시) |
| NFR-05 | DB 접근은 pg 커넥션 풀(`pg.Pool`)을 사용하며 최대 커넥션 수는 설정값으로 둔다(기본 20, 가정). 요청마다 커넥션을 새로 생성하지 않는다. | 코드 리뷰, DB 커넥션 수 모니터링 |
| NFR-06 | 할일 목록 API는 페이지네이션을 적용한다(기본 50건, 최대 100건, 가정). 캘린더 API는 조회 기간(뷰 범위)으로 결과를 제한한다. | 코드 리뷰 |
| NFR-07 | 주요 조회 조건(소유 사용자, 기간, 카테고리)에 인덱스를 둔다. 주요 쿼리는 Seq Scan 없이 실행된다. 인덱스 상세는 후속 DB 설계 문서에서 정의. | `EXPLAIN` 확인 |
| NFR-08 | 프론트엔드는 TanStack Query 캐싱으로 동일 데이터 중복 요청을 줄인다(화면 전환 시 재요청 최소화). | 브라우저 네트워크 탭 |

### 4.2 보안
| ID | 요구사항 | 측정 방법 |
|----|----------|-----------|
| NFR-09 | 비밀번호는 **bcrypt(cost 10, 가정)** 해시로만 저장하며 평문·복호화 가능한 형태로 저장·로그 출력하지 않는다. | 코드 리뷰, DB 확인 |
| NFR-10 | 인증은 **JWT Access Token(HS384, 만료 15분, 가정)** 을 `Authorization: Bearer` 헤더로 전달하고, **Refresh Token(Must, 만료 14일, 가정)** 으로 Access Token을 자동 갱신한다. Access Token은 클라이언트 메모리에만 두고, Refresh Token은 서버가 폐기 여부를 확인하는 불투명 무작위 문자열로 클라이언트 localStorage에 저장하며 DB에는 해시만 저장한다. Refresh Token은 회전하지 않는다(만료까지 같은 토큰 재사용). 근거: 보호 요청 검증은 서명만 확인해 무상태로 처리하고(수평 확장 유리), 세션 폐기는 Refresh Token 행 삭제로 처리한다. 로그아웃은 서버의 Refresh Token 폐기 + 클라이언트 토큰 폐기로 처리한다(A-14). 비밀번호 변경 시 해당 사용자의 모든 Refresh Token을 폐기한다. | 인증 없는 요청 401, HS384 외 알고리즘 서명 토큰 401, 로그아웃 후 refresh 401 확인 |
| NFR-11 | 모든 SQL은 pg **파라미터화 쿼리**(`$1, $2 …`)로 실행하며 사용자 입력을 문자열 결합하지 않는다. | 코드 리뷰 |
| NFR-12 | BR-02를 **서버에서 강제**한다: 모든 할일·카테고리 쿼리는 토큰의 사용자 ID로 소유자 조건을 건다. 타인 리소스 접근 시 404를 반환한다(존재 여부 비노출). | 타 사용자 ID로 접근 테스트 |
| NFR-13 | 서버는 모든 입력을 검증한다(BR-07, BR-10, BR-11 등). 클라이언트 검증은 UX 보조일 뿐이다. | API 직접 호출 테스트 |
| NFR-14 | 운영 환경은 HTTPS로 제공하고, JWT 비밀키·DB 접속 정보는 환경변수로 관리하며 저장소에 커밋하지 않는다. | 설정 확인 |
